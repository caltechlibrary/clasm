- [x] Restore OpenSearch Snapshot from S3 leaves the local snapshot repository unwritable by OpenSearch, so the *next* Archive OpenSearch Snapshot on the same instance always fails -- and fails with a 404 that names nothing useful. `buildSyncFromS3Command` (`internal/workflow/restore_opensearch.go:27`) runs `aws s3 sync` over SSM, which executes as **root on the host**, so every file and directory it writes into the repo directory is `root:root`; OpenSearch runs as uid 1000 inside the `search` container and can only write where the retrofit runbook's one-time `chown 1000:1000` reaches -- the top-level directory. ## Nice to have

- [ ] `RunShellCommand`'s (`ssm.go`) client-side timeout never actually cancels the underlying SSM command on the instance -- it only stops clasm's own `GetCommandInvocation` polling loop and reports a "timed out" error, while the real remote command can keep running to completion (or failure) entirely invisibly. Found real, live, 2026-08-18: Restore SQL Backup's load step timed out client-side at the (then-too-short) 30-minute bound against `caltechdata-restore-test`, but `ps aux` on the instance showed the actual `psql` load process still genuinely running and making progress (80 tables already created) well past that point -- the operator has no way to know from clasm's own "timed out" message whether the operation actually stopped or is quietly still in flight. General design question for a future pass, not fixed here: should a client-side timeout also issue `ssm:CancelCommand` so "timed out" reliably means "stopped," or should clasm instead surface "this may still be running on the instance, check manually" rather than a bare timeout error? Related to (but distinct from) the already-filed `RunShellCommand`-stdout-only-capture gap above/below -- both are about this same helper's error/status reporting not fully reflecting reality. **Update 2026-08-19:** the specific incident this bullet describes turned out to have a second, AWS-side cause on top of the client-side gap -- see the newly-fixed `TimeoutSeconds` bug above (Phase 20.61). AWS's own SSM execution did eventually kill the real remote process, just later (1 hour) than the client had already given up (30 minutes then, now synced to the same value as the client timeout). This bullet's own open question -- whether a client-side give-up should also proactively `ssm:CancelCommand` -- remains open and unresolved by that fix.
- [ ] `RunShellCommand` (`ssm.go`) only ever returns a remote command's `StandardOutputContent` -- `StandardErrorContent` is captured by SSM but discarded entirely, project-wide, in every one of this codebase's SSM-driven commands. Most shell tools' own error text lands on stderr by default (confirmed real, 2026-08-18: `gunzip`'s "unknown suffix" message during a live Restore SQL Backup test, see Phase 20.59), so any command whose *failure* text matters can report only a bare "(status: Failed)" with the real explanation invisible unless a caller happens to redirect stderr into its own command string (as Phase 20.59's fix now does for four of `restore_sql.go`'s own commands). A general fix would widen `RunShellCommand` to return stderr separately (not merged into stdout, since some callers -- `detectExistingSQLData`/`countRestoredTables`, and likely others across the codebase -- parse stdout content for meaningful data on success and can't risk a stray stderr notice corrupting that), then let each caller decide whether/how to fold it into its own error message. Would touch every existing `RunShellCommand` call site (a mechanical but wide ripple across `internal/workflow`). Not scoped or designed yet.
- [ ] `checkCloudInitCompletion` (`cloud_init_check.go`) collapses cloud-init's own `--wait` exit code to a flat "done" or "error, check the instance before using it" -- but cloud-init distinguishes exit 0 (clean) from exit 2 ("degraded": completed, but at least one module reported a non-fatal `recoverable_errors` warning). Found 2026-08-18 launching a fresh dev/restore-test instance (`caltechdata-restore-test`, `i-0f2483bb0885836e5`) from `granian-rdm-v14/cloud-init.yaml`: clasm reported "cloud-init reported an error -- check the instance before using it" for what turned out to be two entirely harmless `groups:` warnings ("Skipping creation of existing group 'staff'/'www-data'", both pre-existing on stock Ubuntu) -- `errors: []` was empty the whole time. Required a full SSM session + `cloud-init status --long` to confirm it was a false alarm rather than a real failure. Fix: have `CloudInitCheckResult` distinguish "degraded" (exit 2, only `recoverable_errors`) from a hard error (exit 1, or anything in `errors`), and surface the actual `recoverable_errors`/`errors` text in the reported message instead of the generic "check the instance" -- same "don't hide the real error behind a generic message" lesson as the 2026-07-29 `curl -fsS`/OpenSearch fix (DECISIONS.md, "Real bug: `curl -fsS` hid OpenSearch's own error body..."). Not scoped or designed yet.
